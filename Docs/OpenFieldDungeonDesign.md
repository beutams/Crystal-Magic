# Open Field Dungeon Design

## Status

This document records the approved direction for replacing the room-and-corridor dungeon with a single-layer, open-field dungeon.

- Normal floors use fBm Perlin terrain.
- One theme covers a floor band, normally floors 1-10, 11-20, and so on.
- Every tenth floor is a boss floor, but it still uses the same random open-field terrain instead of a fixed room prefab.
- The existing room, corridor, ante-room, door, room profile, three-level treasure pool, and fixed boss-room concepts are retired for normal open-field floors.

This is a design document only. It does not itself change the runtime generator.

## 1. Map Model

### 1.1 Cell types

Every map cell has one terrain type:

| Cell type | fBm source band | Movement | Blocks line of sight | Visual purpose |
| --- | --- | --- | --- | --- |
| Void | Low | Blocked | No | Bottomless area / map boundary |
| Ground | Middle | Walkable | No | Main combat and exploration space |
| Obstacle | High | Blocked | Yes | Cliff, rock wall, or solid terrain blocker |

`Ground` is the only walkable terrain for fBm maps. Both `Void` and `Obstacle` require movement blocking. `Obstacle` also writes to the line-of-sight blocker mask for combat ray tests.

### 1.2 Generation order

```text
Candidate seed
  -> fBm height sampling
  -> Low/Middle/High classification
  -> Void/Ground/Obstacle masks
  -> place entrance and interest points
  -> choose one large interest point as the exit interest point
  -> BFS from entrance verifies every interest point and exit are reachable
  -> generate squads, chests, landmarks, and wild monsters
  -> build runtime scene spawn data
  -> accept seed
```

The generator advances to the next deterministic seed whenever a placement, reachability, squad footprint, or content placement check fails. It must not fall back to a lower-quality candidate.

### 1.3 Interest points

Interest points replace rooms, halls, and ante-rooms.

- Small, medium, and large interest points are circular or footprint-based ground reservations.
- Their full reserved area must be ground. They cannot overlap void or obstacle cells.
- Each point has a stable `EncounterId`.
- The entrance is a safe point record. One large interest point is selected as the exit interest point; the exit is placed inside its reserved ground area.
- The exit interest point always generates exactly one guarding large squad. The exit shares that squad's `EncounterId` and opens only after every monster with that id dies.
- The entrance BFS validates that every interest point and the exit interest point can be reached.

## 2. Theme Data

`DungeonThemeData` remains the root record and still owns a floor range. A theme is selected for the current floor exactly as it is today.

The old `VisualStyles`, room visuals, corridor visuals, wall tiles, door tiles, room profiles, ante-room profiles, `Mob1PoolId`, `Mob2PoolId`, `Mob3PoolId`, treasure pool ids, and boss-room ids are replaced by theme-owned open-field data.

```text
DungeonThemeData
  Id, Name, ThemeKey, FloorStart, FloorEnd
  OpenFieldVisual
  OpenFieldInterestLandmarks
  EncounterConfig
  TreasureConfig
```

### 2.1 Terrain visual data

```text
OpenFieldVisualData
  VoidTileGrid       // Existing 3 x 3 tile-grid data format
  GroundTileGrid     // Existing 3 x 3 tile-grid data format
  ObstacleTileGrid   // Existing 3 x 3 tile-grid data format
```

All three terrain types use the current 3 x 3 tile-grid representation. The tile resolver reads neighboring terrain types to choose corners, edges, and center tiles.

- Ground tiles render the playable floor.
- Obstacle tiles render cliffs or blocking terrain and create rectangle collision spawns.
- Void tiles render the visual void and outer transition. Void also receives an invisible blocking boundary or collision representation so units cannot leave ground.

### 2.2 Interest landmarks

An interest point is not a room prefab. It is a ground reservation with a small number of individually placed building or landmark prefabs near its center.

```text
OpenFieldInterestLandmarkSet
  SmallEntries[]
  MediumEntries[]
  LargeEntries[]

LandmarkEntry
  PrefabName
  Weight
  FootprintWidth, FootprintHeight
  ApplyCollider
  MinInstances, MaxInstances
```

The placer chooses a few weighted entries and validates their footprints against ground, the interest-point reservation, and existing placements. The resulting prefabs act as recognizable human-made landmarks, not as pre-authored rooms.

## 3. Encounter and Squad Data

### 3.1 Data hierarchy

Regular monsters are generated by squads, not by independent per-cell monster rolls.

```text
Theme
  EncounterConfig
    SmallInterestPool
      Squad A
        footprint: 3 x 3
        weight
        level: 1 / 2 / 3
        members[]
      Squad B
        ...
    MediumInterestPool
      squads[]
    LargeInterestPool
      squads[]
```

For an interest point, its size selects one pool. The generator chooses one squad by positive weight and then spawns every member entry in that squad. A squad therefore keeps a coherent encounter style: a goblin squad stays a goblin squad and does not become an accidental goblin-and-spider mixture.

### 3.2 Squad records

```text
DungeonEncounterPoolData
  InterestSize: Small / Medium / Large
  Squads[]

DungeonSquadData
  Name
  Weight
  MonsterLevel: 1 / 2 / 3
  IsBossSquad
  Width, Height
  Members[]

DungeonSquadMemberData
  UnitName
  Count
```

`Width` and `Height` describe the usable squad deployment area in map cells. Example: a 3 x 3 squad with one member entry of `Goblin x 4` randomly places four 1 x 1 goblins inside the 3 x 3 footprint.

### 3.3 Unit footprint

Every monster prefab gets a new `UnitDungeonFootprintFeatureAuthoring` component. Its paired `UnitDungeonFootprintModuleData` appears in UnitEditor only when that authoring component exists.

```text
UnitDungeonFootprintModuleData
  Width = 1
  Height = 1
```

The squad placer reads this module through the unit data table. It must reserve the full rectangular unit footprint, reject overlap with another member, reject non-ground cells, and keep the result inside the squad footprint.

Every generated squad receives a stable, layout-local `SquadId`. Each monster placement carries both `EncounterId` and `SquadId`: `EncounterId` links the exit to its guarding squad, while `SquadId` identifies squadmates for later group-AI communication, shared alerts, target selection, or formation behavior.
The existing UnitEditor extension pattern should be used:

1. Add one feature authoring component to the unit prefab.
2. Add one module data type to `UnitData`.
3. Add one UnitEditor attribute drawer detected from that feature.
4. Bake an ECS footprint component only if runtime systems later need the size; the generator itself only needs the data-table module.

### 3.4 Three monster levels

The existing `MOB1`, `MOB2`, and `MOB3` semantics remain. The level belongs to a squad, rather than creating separate editor trees for each level.

- The small, medium, and large pools control encounter size and map placement.
- The squad level controls difficulty, UI, analytics, and any level-based monster-pool filtering.
- A theme can contain different level-appropriate squads in the same size pool, with floor-range filtering where required.
- Wild monsters use a dedicated low-threat squad pool and should normally be level 1.

This keeps both necessary dimensions: interest-point size and monster difficulty.

## 4. Treasure Data and Luck

Treasure no longer has three dungeon levels, money rewards, quantities, or per-entry chance fields.

```text
Theme
  TreasureConfig
    CandidateItemIds[]
    ChestLuckMin
    ChestLuckMax
```

- The editor lists only candidate items for the selected theme.
- Every item is granted as one item.
- `ItemData.Rarity` is the only source of item rarity.
- Every generated chest stores its own integer or float `Luck` value.
- The chest selection normalizes calculated weights; it does not store an authored chance per item.

Recommended luck weighting, where larger `Rarity` means rarer:

```text
maxRarity = maximum rarity among all candidate items
baseWeight(item) = maxRarity + 1 - item.Rarity
effectiveWeight(item, luck) = baseWeight(item) + luck * item.Rarity
probability(item) = effectiveWeight(item, luck) / sum(all effective weights)
```

At luck `0`, common items have the larger weight. Increasing luck raises rare-item weights faster, so rare items become relatively more likely without needing authored per-item chances. The exact luck range and scale should be exposed in the theme treasure settings.

## 5. Boss Floors

Boss floors use the same fBm map, interest-point placement, and squad data as normal floors. They do not use a fixed room prefab or a separate boss configuration.

1. Generate the same fBm map.
2. Require at least one large interest point and select one as the exit interest point.
3. Place the exit inside that point and assign it the point's guarding `EncounterId`.
4. From that theme's `LargeInterestPool`, choose a weighted squad with `IsBossSquad = true` for this point.
5. The exit opens through the ordinary encounter-clear rule once that squad dies.

`DungeonSquadData.IsBossSquad` is only enabled for boss candidates. Normal floors choose a non-boss large squad for their exit interest point. A boss squad's `Members[]` may contain the boss itself and any support units. Every member uses its unit-owned drop table: boss-only rewards use item entries with chance `1`, and ordinary monsters can use chance-based material and money entries. Chest luck never modifies unit drops. This is the only BOSS-layer difference; exit placement, locking, and encounter identifiers use the same logic on every floor.
## 6. DungeonEditor Redesign

The editor keeps its existing two-panel form: a theme list on the left and the selected theme's detail panel on the right. Every main page uses the same selected theme.

### 6.1 Main pages

| Page | Left list | Right panel |
| --- | --- | --- |
| Theme | Themes | Basic floor range, terrain tile grids, interest landmark sets |
| Encounters | Themes | Small / Medium / Large squad pools, squads, and squad members |
| Treasure | Themes | Candidate item list and chest luck range |


### 6.2 Theme page subpages

```text
Overview
Terrain Tiles
Interest Landmarks
```

Remove the old visual-style, wall-tile, door-tile, room-profile, and ante-room-profile subpages.

### 6.3 Encounter page layout

```text
Theme selected on the left
  -> size tabs: Small / Medium / Large
  -> squad list for the chosen size
  -> selected squad detail
     -> weight, level, deployment width, deployment height
     -> member list: unit selector + count
     -> boss candidate checkbox
```

Squads and members use foldouts. This makes a theme with many squads navigable while keeping the requested hierarchy visible.

The same squad editor exposes `IsBossSquad`. Boss squads belong to the large interest-point pool and are excluded from ordinary encounter selection. Drops are not edited here: selecting the boss or monster unit in UnitEditor exposes its own drop table, including material, money, probability, and quantity settings.

### 6.4 Treasure page layout

The right panel has one item list with add/remove controls and a chest-luck range. The item selector excludes money and records only item ids.


## 7. Runtime Code Design

### 7.1 New pure generator

Extract the current MapTest fBm logic into a non-MonoBehaviour generator:

```text
OpenFieldDungeonGenerator
  GenerateCandidate(seed, config, theme)
  BuildHeightMap(...)
  ClassifyTerrain(...)
  PlaceEntranceAndInterestPoints(...)
  SelectExitInterestPoint(...)
  ValidateReachability(...)
  PlaceLandmarks(...)
  PlaceSquads(...)
  PlaceChests(...)
  PlaceWildSquads(...)
```

The MapTest component becomes a preview client of this generator. It must not be the production generator.

### 7.2 Layout and runtime scene data

Create `OpenFieldDungeonLayout` for terrain, points, encounter ids, and content placements. Do not force this data into `DungeonMakerTunnelingResult` because that legacy type cannot represent void and obstacle semantics separately.

`RuntimeDungeonSceneData` remains the runtime contract. Add a dedicated `BuildOpenFieldSceneData(layout, floor, theme, config)` path that produces:

- Floor and terrain tile spawns.
- Hidden rectangle collision spawns for void boundaries and obstacles.
- Landmark environment spawns.
- Entrance world position.
- Exit scene-object spawn inside its large interest point with the guard squad's encounter id.
- Treasure scene-object spawns with resolved item rewards.
- Monster spawn data with encounter id, squad id, and level.

`DungeonSceneRuntimeBuilder` can continue to instantiate tiles, environment, scene objects, player, and monsters from `RuntimeDungeonSceneData`.

### 7.3 Encounter ids

The current field name `RegionId` is room-oriented, but the exit system only needs a shared integer between the exit and its living monsters. Open-field code should treat this as `EncounterId`.

Short-term compatibility: continue filling the existing `RegionId` fields with an interest-point encounter id.

Later cleanup: rename `RegionId` to `EncounterId` in runtime spawn data, exit components, monster spawn components, and the exit system.

### 7.4 Squad ids

Add `SquadId` to open-field monster spawn data and the resulting monster component. It is unique within one generated layout and is separate from `EncounterId`: the exit system observes only `EncounterId`, while AI systems can query `SquadId` to find nearby squadmates without coupling group behavior to exit rules.

### 7.5 Loading progress

The transition generator already runs as a coroutine. The open-field replacement should yield after height-map row batches and after each major phase:

```text
0.28  Preparing seed
0.35  Sampling fBm height map
0.50  Classifying terrain and collision masks
0.62  Placing entrance and interest points, then selecting the exit interest point
0.74  Verifying reachability
0.84  Placing squads, chests, landmarks, and wild monsters
0.92  Building runtime scene data
0.99  Runtime scene construction
```

Rejected seeds publish the attempt number and continue. This keeps the Loading screen responsive even when many seeds are rejected.

## 8. Migration Plan

1. Add the open-field layout data, pure fBm generator, and deterministic tests without touching the live transition path.
2. Change MapTest to consume the pure generator and validate preview parity.
3. Add theme-owned terrain, landmark, encounter, and treasure data. Build the redesigned DungeonEditor against those data objects. Boss eligibility belongs to squad data; rewards remain unit-owned drop-table data.
4. Add unit dungeon-footprint authoring, unit data module, and UnitEditor drawer. Fill footprint data for all dungeon monsters.
5. Implement `BuildOpenFieldSceneData` and verify real tiles, collisions, player, exit, chest, squad, and boss spawning in the dungeon scene.
6. Route non-boss floors in `DungeonGenerationService` to the new open-field generator. Keep existing fixed boss generation active temporarily.
7. Route boss floors through the same generator, selecting a boss-enabled large squad for the exit interest point. Do not add a separate boss-exit branch.
8. Remove the old normal-floor room generator, room scoring, room visual config, old monster-pool tables, old treasure-pool tables, and boss-room geometry only after migration validation is complete.

## 9. Required Validation

- Same floor and seed always produce the same layout, content, squad positions, chest luck, and boss.
- Every accepted map has a path from entrance to exit and all interest points.
- Every squad member footprint is fully on ground and does not overlap another member, landmark, chest, entrance, or exit.
- Void and obstacle both block movement; obstacle blocks line of sight.
- Every exit is inside a large interest point and remains closed while any monster in its guarding encounter id is alive.
- Boss and normal monster drops use their unit-owned drop tables; BOSS-only item entries can be guaranteed and are unaffected by chest luck.
- Monsters spawned by a squad share that squad's `SquadId`, independently of the exit `EncounterId`.
- No room, corridor, door, or ante-room data is needed to build a normal floor.
